# 技术设计：修复 v3.8.0-beta.3 虚拟支付相关问题（#1186 / #1179 / #1181）

> **时间**：2026-08-23
> **作者**：GLM-5.3 + yansongda
> **状态**：经过人工审核确认

---

## 1. 背景与问题

**现状**：v3.8.0-beta 系列引入了类型化 Config 体系与微信小程序虚拟支付。`Pay::config()` 构造 `Config` 对象时会对**所有已传入的 provider 配置**立即实例化并校验（`AbstractConfig::__construct` 调用 `validateRequired()`）；虚拟支付服务端 API（`/xpay/*`）要求调用方手动传入 `access_token`；客户端签名（`requestVirtualPayment`）对 signData 的字段顺序敏感但未做任何规范化。

**困境**（issue #1186 / #1179 / #1181 反馈）：

1. **配置急切校验误伤**（#1186-①）：官方文档 `init.md` 的示例配置本身就是 alipay+wechat 完整骨架，用户复制后只填 wechat 部分，`Pay::config()` 即抛 `缺少支付宝配置 -- [app_id]`。用户被迫给不用的 provider 填假值。
2. **signData 字段顺序陷阱**（#1186-②、#1181）：`paySig = HMAC-SHA256(uri + '&' + JSON(signData), app_key)`，Midas 验签对 key 顺序敏感，而 SDK 按用户传参顺序原样序列化，顺序随传参漂移；文档只字未提，用户排查多日。#1181 进一步提出 NFR：SDK 生成签名时对 body 做字典排序，从根上消除顺序问题。
3. **access_token 无自动管理**（#1186-③、#1179 同源）：`AddPayloadSignaturePlugin` 对服务端 API 强制要求手动传 `access_token`（每次调用、需自管缓存），文档示例也未提及；而 SDK 对 PayPal / Airwallex 已有成熟的 token 自动获取+缓存惯例。#1179 与 #1186-③ 报错位置完全相同（`AddPayloadSignaturePlugin.php:46`），作者已确认需手动获取。

**目标约束**：

- **向后兼容**：现有手动传 `access_token`、现有完整配置的用法行为不变
- **遵循惯例**：token 管理完全复刻 `PaypalTrait`/`AirwallexTrait` 既有模式，不发明新机制
- **异常消息不变**：问题 1 修复后，报错文案保持原样，仅推迟抛出时机

## 2. 整体方案

**核心思路**：四个修复独立推进--① 把配置校验从「构造期」推迟到「获取期」（惰性校验）；② 复刻 PayPal token 模式为虚拟支付增加 `stable_token` 自动获取与进程内缓存；③ 客户端签名场景对 signData 做字典序规范化并在返回结果中提供与签名逐字节一致的 `signData` JSON 字符串；④ 文档补齐 signData 顺序、offerId 类型与 token 说明。

### 校验链路对比

```
【现在】
Pay::config($config)
  └─ new Pay\Config($config)
       └─ new AlipayConfig(...) ──> validateRequired() ❌ 立即抛错（即使只用微信）
       └─ new WechatConfig(...) ──> validateRequired()

【改后】
Pay::config($config)
  └─ new Pay\Config($config)
       └─ new AlipayConfig(...)   ✅ 仅实例化，不校验
       └─ new WechatConfig(...)   ✅ 仅实例化，不校验

Pay::alipay()->web($order)         （真正使用时）
  └─ 插件 -> ProviderConfigTrait::getProviderConfig('alipay')
       └─ $config->validate() ❌ 此时报"缺少支付宝配置 -- [app_id]"（消息不变）
```

### access_token 获取链路

```
AddPayloadSignaturePlugin（服务端 API 场景，uri != requestVirtualPayment）
  ├─ payload 已有 access_token ──────────────> 直接使用（现状，不变）
  └─ 无 access_token
       ├─ 已配置 virtual_pay.app_secret
       │    ├─ WechatConfigVirtualPay 缓存未过期 ──> 返回缓存 token
       │    └─ 无缓存/过期
       │         └─ Artful::artful([StartPlugin,
       │              Virtual/GetAccessTokenPlugin,      ← 新增
       │              AddPayloadBodyPlugin, AddRadarPlugin,
       │              ResponsePlugin, ParserPlugin])
       │           POST https://api.weixin.qq.com/cgi-bin/stable_token
       │           └─ 回写缓存（提前 300 秒过期）-> 返回 token
       └─ 未配置 app_secret ──> 抛 InvalidParamsException（消息指明两条出路）
```

### signData 规范化链路（客户端签名场景）

```
用户传参（任意顺序）
  └─ PayPlugin（客户端场景）
       └─ 业务字段(非 _ 前缀) 递归 ksort(SORT_STRING) ──> 重组 payload
            └─ AddPayloadBodyPlugin 打包 _body（天然字典序）
                 └─ AddPayloadSignaturePlugin
                      ├─ paySig = HMAC(uri + '&' + _body, app_key)
                      └─ mergePayload(['signData' => _body, ...])   ← 新增
                           └─ 返回前端：signData 字符串 + paySig + signature
                                └─ 前端 wx.requestVirtualPayment({ signData: 原样传递 })
```

## 3. 详细设计

### 3.1 问题 ①：配置惰性校验

**做什么**：校验从「构造 Config 对象时」移到「通过 `getProviderConfig()` 获取时」。

**怎么做**：

```php
// AbstractConfig
__construct(values, tenant):
    unserializeArray(values)   // 删除 validateRequired() 调用
public validate(): void:
    validateRequired()         // 新增公开入口，幂等可重复调用

// ProviderConfigTrait::getProviderConfig() / Config::getProviderConfig()
// 两个同名入口统一语义为「获取即校验」，返回前追加：
$providerConfig->validate()
// trait 版取值为 null（Provider 或租户不存在）时抛语义化
// InvalidConfigException（与 Config::getProviderConfig 现有行为一致），
// 避免「Call to a member function on null」级 Fatal Error
```

**边界**：

- 各 Config 的 `validateRequired()`（含 `d85b3375` 引入的 `validateNotEmpty()` 声明、Wechat 的 32 字节长度校验与服务商模式校验、Unipay 的沙箱跳过逻辑）**全部原样保留**，仅调用时机变化
- WechatConfig 构造期的 CertManager 证书导入副作用（setter 内）保留在构造期，不受影响
- `HttpConfig`/`LoggerConfig` 的空实现 `validateRequired()` 不受影响
- 校验开销：每次 `getProviderConfig()` 增加数个 `empty()` 检查，纳秒级，可忽略
- `d85b3375` 刚移除的 `validateForV2/Mp/Mini` 是无调用的死代码；新 `validate()` 被 `getProviderConfig()` 实际调用，且是所有插件获取配置的唯一入口（已验证：全库 `ConfigInterface::class` 引用仅 `ProviderConfigTrait` 与 `Pay.php` 两处）

**行为对比**：

| 场景 | 现在 | 改后 |
|---|---|---|
| `Pay::config()` 只配 wechat（附空 alipay 骨架） | ❌ 抛「缺少支付宝配置」 | ✅ 成功 |
| `Pay::config()` 配置完整 | ✅ 成功 | ✅ 成功（不变） |
| `Pay::alipay()` 时 alipay 配置缺失 | 不会到达（config 阶段已抛） | ❌ 调用时抛，**消息与现在完全一致** |

### 3.2 问题 ③：access_token 自动管理

**配置结构**（`virtual_pay` 新增 `app_secret`，完整示例）：

```json
{
  "wechat": {
    "default": {
      "mch_id": "1900000000",
      "mch_secret_key": "（32字节APIv3密钥）",
      "mch_secret_cert": "（私钥路径）",
      "mch_public_cert_path": "（证书路径）",
      "notify_url": "https://example.com/notify",
      "mini_app_id": "wx1234567890abcdef",
      "virtual_pay": {
        "app_key": "虚拟支付AppKey",
        "sandbox_app_key": "沙箱AppKey（可选）",
        "offer_id": "虚拟支付商户号",
        "app_secret": "小程序AppSecret（新增，启用token自动获取）",
        "encoding_aes_key": "回调解密密钥（可选）",
        "callback_token": "回调校验Token（可选）"
      }
    }
  }
}
```

| 新增字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `virtual_pay.app_secret` | string | ❌ | 小程序 AppSecret；配置后服务端 API 无需手动传 `access_token` |

`WechatConfigVirtualPay` 另新增运行时缓存字段 `$_accessToken` / `$_accessTokenExpiry`（私有 + getter/setter，命名与 `PaypalConfig` 完全一致）。副作用：用户也可通过 `virtual_pay.access_token` + `virtual_pay.access_token_expiry` **预置** token（适合自有中控 token 服务的用户），与 PaypalConfig 行为一致。

**token 请求管道**（与 `PaypalTrait::getPaypalAccessToken()` 同构）：

```php
// WechatTrait::getWechatVirtualAccessToken(array $params): string
if 缓存命中(token非空 且 expiry非空 且 time() < expiry): return 缓存   // 单缓冲，对齐 PaypalTrait
if app_secret 或 mini_app_id 为空: throw InvalidConfigException（指明缺失字段）
result = Artful::artful([
    StartPlugin, Virtual/GetAccessTokenPlugin, AddPayloadBodyPlugin,
    AddRadarPlugin, ResponsePlugin, ParserPlugin
], ['_config' => tenant, grant_type: 'client_credential', appid: mini_app_id, secret: app_secret])
if result.access_token 为空: throw InvalidResponseException（含 errcode/errmsg）
写回缓存 expiry = time() + (expires_in ?? 7200) - 300; return token
```

- **插件职责**：`GetAccessTokenPlugin` 仅设置 `_method=POST`、`_url=/cgi-bin/stable_token`；body 参数由 trait 经 params 注入--与 Paypal 插件职责划分一致
- **干净 params**：微信 stable_token 的 credentials 必须走 JSON body（不同于 PayPal 的 Authorization Basic 头模式），因此 trait **不透传业务 params**，仅构造 `['_config' => 租户, grant_type, appid, secret]`，避免 openid 等业务字段混入 token 请求体（StartPlugin merge 后由 AddPayloadBodyPlugin 的 `filter_params` 打包，`_config` 前缀字段被自动滤除）
- **提前 300 秒过期（单缓冲）**：官方文档明确「普通模式下平台会提前 5 分钟更新 access_token」；有效期 7200s；`expires_in` 缺省取 7200。缓存命中条件与 `PaypalTrait` 一致（token 非空 + expiry 非空 + 未过期，仅写回时提前 300 秒、命中时不重复扣减）
- **失败处理**：微信 cgi-bin 错误为 HTTP 200 + `{errcode, errmsg}`，`ResponsePlugin`（仅查 HTTP 状态码）拦不住，故由 trait 显式检查 `access_token` 为空即抛 `InvalidResponseException`（携带 errcode/errmsg）。此项是对 Paypal 模式的小幅改进（Paypal 空 token 会继续发业务请求、报出误导性错误）
- **缓存作用域**：config 对象（进程内、租户隔离）。多进程部署各进程独立获取；`stable_token` 幂等设计（`force_refresh=false` 尽量返回相同 token、与普通 token 不互踢、频控 1 万次/分钟）天然容忍此模式

**`getWechatUrl()` 路由规则**（新增 `/cgi-bin/` 分支）：

```
'http' 开头               -> 原样返回                [现有]
'requestVirtualPayment'   -> 原样返回（客户端签名）   [现有]
'/xpay/' 前缀             -> URL_VIRTUAL             [现有]
'/cgi-bin/' 前缀          -> URL_VIRTUAL             [新增]
其它                      -> Wechat::URL[mode]       [现有]
```

**`AddPayloadSignaturePlugin` 修改**（服务端 API 场景）：

```php
if payload 无 access_token:
    if 配置了 virtual_pay.app_secret:
        accessToken = getWechatVirtualAccessToken(params)
    else:
        throw InvalidParamsException(
            '参数异常: 微信虚拟支付缺少 access_token，'
            + '请配置 [virtual_pay.app_secret] 以自动获取，或在参数中手动传入 access_token')
```

### 3.3 问题 ②：signData 字典序规范化（#1186-②、#1181）

**做什么**：客户端签名场景（`requestVirtualPayment`，SDK 不发 HTTP 请求、仅生成签名数据返回前端）对参与签名的业务字段做递归字典排序，并在返回结果中提供与签名逐字节一致的 `signData` JSON 字符串。

**怎么做**：

```php
// PayPlugin（客户端场景）：mergePayload 后重排 payload
业务字段(非 _ 前缀) -> 递归 ksort(SORT_STRING) -> 与 _ 前缀字段重组
// 之后 AddPayloadBodyPlugin 打包的 _body 天然字典序
// 返回给前端的 destination 字段顺序 = 签名顺序（自洽）

// AddPayloadSignaturePlugin（客户端场景）：mergePayload 追加
'signData' => $body    // 即 _body 字符串，与 paySig 签名输入逐字节一致
```

**三层保障**：

1. **字典序规范化**：signData 顺序不再依赖用户传参顺序（Java TreeMap 同思路，有沙箱实战成功案例）
2. **`signData` 字符串原样传递**：前端 `wx.requestVirtualPayment({ signData: result.signData, paySig: result.paySig, ... })`，签名与传递的字符串逐字节一致，同时消除 JSON 转义差异（如 PHP `\/` 与 JS `/`）
3. **文档说明**：自行构造对象时字段顺序必须与返回顺序（字典序）一致；`offerId` 必须为字符串类型（数字签名失败，现有实现从配置取值已是字符串）

**边界**：

- 服务端 API 场景（`/xpay/*`）**不做**排序：body 自签自发，微信按收到的原文验签，顺序无关
- `signData` 字段在签名计算之后 merge 进 payload，不会混入 body
- `paySig`/`signature`/`signData`/`env` 等返回字段均为 merge 产物，不参与 body 打包

**行为变更**：返回字段顺序变为字典序。前端动态使用 SDK 返回字段的用户零改动；hardcode 顺序的需按新顺序调整（CHANGELOG 标注，beta 阶段可接受）。

### 3.4 问题 ④：文档补充

**`virtual.md` 客户端签名节**新增 warning：

> `paySig = HMAC-SHA256(uri + '&' + signData的JSON字符串, app_key)`，Midas 验签对 key 顺序敏感。SDK 已自动对 signData 做字典序排序，并返回与签名逐字节一致的 `signData` JSON 字符串--**优先直接使用** `wx.requestVirtualPayment({ signData: result.signData, ... })` 原样传递，切勿重新序列化。如需自行构造对象，字段名、值、顺序必须与返回结果完全一致。注意 `offerId` 必须为字符串类型。

**`virtual.md` 服务端 API 节**新增说明：

- 配置 `virtual_pay.app_secret` 后 SDK 自动获取并缓存 `access_token`（stable_token 接口，提前 5 分钟刷新）
- 也可在参数中手动传入 `access_token`（优先级高于自动获取）；适合自有中控 token 服务的用户
- **IP 白名单提示**：小程序后台若配置了 IP 白名单，获取 token 的服务器 IP 不在名单内会报 `errcode 40164`
- **第三方平台代调边界**：stable_token 不支持第三方平台调用；使用 `authorizer_access_token` 代商家调用时必须手动传入 token

**`init.md`**：`virtual_pay` 配置表格补 `app_secret` 行。

## 5. 风险与对策

| 风险 | 严重度 | 对策 |
|---|---|---|
| 惰性校验使 `Pay::config()` 不再提前暴露未使用 provider 的配置错误，依赖此行为的用户感知变化 | 中 | 有意语义修正；CHANGELOG 与升级指南显著标注；实际调用时异常消息与时机精确到具体 provider |
| signData 返回字段顺序变为字典序，前端 hardcode 顺序的用户需调整 | 中 | CHANGELOG 显著标注；前端动态使用返回字段（推荐用法）零改动；新增 `signData` 字符串字段提供最稳传递方式 |
| 进程内缓存导致多进程重复获取 token | 低 | stable_token 幂等 + 1 万次/分钟频控，远超常规业务量；文档说明多进程行为 |
| IP 白名单（40164）导致自动获取失败 | 低 | 异常消息携带 errcode/errmsg；文档注明需将服务器 IP 加入小程序后台白名单 |
| `virtual_pay.access_token` 预置能力成为公开行为后，用户误填导致 token 不刷新 | 低 | 文档注明仅自有中控 token 服务场景使用；缓存命中条件含过期时间检查 |
| 开启 Artful 日志（`logger.enable=true`）时，token 请求 body 含 `app_secret`，会随 `rocket` 日志明文落盘 | 低 | 日志默认关闭（`logger.enable=false`）；SDK 日志携带完整请求负载属既有机制，文档/CHANGELOG 注明开启日志时的敏感信息风险 |
| stable_token 在虚拟支付场景实测异常（残余风险） | 低 | 官方文档推理链已确认；手动传入口子保留；切换普通 token 接口仅改一处 |
| 字典排序后微信验签仍不通过（微信端非字典序的极端可能） | 低 | 实战文章字典序方案已沙箱验证成功；`signData` 字符串原样传递不依赖任何排序假设（字符串逐字节一致） |

## 6. 监控与可观测性

开源 SDK 无线上监控诉求，本节裁剪。可观测性依赖：

- **既有 Logger 体系**：token 获取走 Artful 管道，插件自带 `Logger::debug/info` 日志（与现有 Virtual 插件一致），token 失败时异常消息含 errcode/errmsg
- **测试**：各阶段各自 `composer test` 全绿为质量门禁
